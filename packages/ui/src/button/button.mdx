# Button

Base UI's [Button](https://base-ui.com/react/components/button), a native
`<button>` that triggers an action on the page. It adds two states the native
element lacks: **disabled but focusable**, from Base UI, so a disabled action
can still be reached and explained, and **pending**, from Osmoz, while the
action runs.

<Canvas of={ButtonStories.Default} />

## Usage

<Guidelines>
  <Guideline when="To run an action with a visible text label.">
    Submit, save, open a dialog, toggle a mode.
  </Guideline>
  <Guideline use={LinkStories} when="To go to another page or URL.">
    A button that navigates breaks middle-click, "open in a new tab" and the screen reader's links
    list.
  </Guideline>
  <Guideline use={IconButtonStories} when="When an icon alone shows the action.">
    Its required `label` is read by assistive technologies.
  </Guideline>
</Guidelines>

## Examples

### Disabled

`disabled` removes the button from the tab order and blocks its click.

<Canvas of={ButtonStories.Disabled} />

### Focusable when disabled

With `focusableWhenDisabled`, a disabled button stays in the tab order and
sets `aria-disabled` instead of `disabled`: the user can reach it and learn why
the action is unavailable. Its click and keys stay blocked.

<Canvas of={ButtonStories.FocusableWhenDisabled} />

### Pending

`pending` marks the action as running: the button sets `aria-busy` and blocks
its click.

<Canvas of={ButtonStories.Pending} />

A pending button stays focusable: the focus does not jump away while the
action runs, and assistive technologies announce it as busy.

## Edge cases

### Pending wins over disabled

`pending` keeps the button busy and focusable, whatever `disabled` and
`focusableWhenDisabled` say: a running action never leaves the tab order.

<Canvas of={ButtonStories.PendingWinsOverDisabled} />

### Never submits its form

Inside a form, a button without `type` runs its action and leaves the form
alone, since `type` defaults to `"button"`.

<Canvas of={ButtonStories.NeverSubmitsItsForm} />

## Keyboard

<Keyboard>
  <Key keys={["Tab"]}>Moves the focus to the button, unless it is `disabled`.</Key>
  <Key keys={["Enter", "Space"]}>Runs the action, unless the button is disabled or pending.</Key>
</Keyboard>

## Accessibility

- The role is the native `button`, so no ARIA role is added.
- `type` defaults to `"button"`, so a button inside a form never submits it by
  accident. Pass `type="submit"` on purpose.
- The accessible name is its text content. The app passes it from its catalog.
- Its content is free: an icon goes before or after the text, wrapped in a
  decorative `Icon`, so it is not read as part of the name.
- `aria-busy` and `aria-disabled` are set by the component: they are not props.

## API

### Props

The props of Base UI's Button, minus `aria-busy`, `aria-disabled`, `render`
and `nativeButton`, plus `pending`. `className` and `style` take a value, not
a function of the state:

<Controls of={ButtonStories.Default} />

### Attributes

The attributes the rendered `<button>` carries in each example. An app styles each
state from them, never from a class:

<Attributes
  stories={[
    ButtonStories.Default,
    ButtonStories.Disabled,
    ButtonStories.FocusableWhenDisabled,
    ButtonStories.Pending,
  ]}
/>

### Styling

The component has no class. Each app styles it in its own
`components/ui/button.tsx`, with a class for every state above:
`data-disabled:`, `aria-busy:`, `focus-visible:`. See each app's section of
this Storybook for its look.

Base UI sets `data-disabled` in every disabled state, focusable and pending
included, while `disabled` and `:enabled` only see the native attribute. A
hover style therefore goes behind `not-data-disabled:hover:`, or a focusable
disabled button would still react to the pointer.
